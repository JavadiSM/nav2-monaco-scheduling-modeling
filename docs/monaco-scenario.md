# Monaco-inspired circuit

## Scene

This is a hand-designed, approximate Monaco silhouette, not an official scaled circuit. Geometry is specified in `config/monaco.yaml` and generated by `scripts/generate_monaco.py`. One red vehicle moves; nineteen blue cars are static models outside the racing corridor. Each static car has a checkpoint association and a reserved edge-worker identity in `scenario.json`.

The centerline is approximately 128.7 m long and the road is 1.30 m wide. There are 19 ordered checkpoints before named turn approaches, followed by a finish target. Start and finish are approximately 3.0 m apart, separated by continuous barriers. A clearance-aware grid search found a roughly 123.1 m shortest traversable route before map wall rasterization; it is a geometric check, not measured robot travel distance. The generator rejects unintended short connections between nearby lanes.

The simulated car is an existing differential-drive TurtleBot with changed visual geometry. Its four visible tires are decorative; physical driving remains the upstream two-wheel differential drive. The upstream collision dimensions, LiDAR, IMU, camera, joints, inertia and drive limits are retained. The body visuals remain below the LiDAR scanning plane so the sensor does not detect the car's cockpit as an obstacle.

Checkpoint 11 uses a 1.50 m approach lead instead of the default 0.55 m. Its target is placed before the chicane's direction reversal, with the incoming heading. The full-course recording predates this placement correction; a focused test passed all three targets (10–12) in 84.2 s; it invoked 0 backup and 0 spin recovery behaviors.

## Navigation configuration

The planner, controller, smoother, behaviors, localization and waypoint follower remain upstream Nav2 components. The project supplies a map, starting pose and ordered `FollowWaypoints` goals; it does not implement its own path-following controller.

Scenario changes relative to installed `nav2_bringup/params/nav2_params.yaml`:

- Local and global inflation radius: 0.34 m; cost scaling: 5.0, to fit the corridor.
- `GridBased.allow_unknown: false`, restricting planning to mapped drivable space.
- Waypoint follower stops on failure; waiting at each waypoint is disabled.
- Simulation time is enabled by launch. Scheduling policies and callback priorities are unchanged.

The occupancy map represents the road as free, physical barriers as occupied and outside space as unknown. Solid-filling outside space as occupied is unsuitable for this AMCL likelihood-field scene: points inside that filled area receive artificially good obstacle-distance scores. World wall coordinates and map pixels share the same transform.

Resource inspection and concrete settings are documented in `docs/resources-and-timing.md`. No per-edge CPU limits or alternative scheduling policies have been enabled.

## Communication and scheduling scope

Communication is feasible through ROS 2 / DDS, but a parked model is only a location and visual identity. Future edge workers need actual processes with explicit resources and interfaces. Several worker processes on one computer can represent servers; resource isolation and link emulation must be specified before claiming heterogeneous execution or realistic networking.

`config/edge_communication.yaml` is inactive. Its null values are intentionally unspecified: publish rate in Hz, bandwidth in Mbps, latency in ms, loss probability and optional coverage radius. Values can later be defined per link. Application-layer emulation and network-layer shaping have different semantics; neither is implemented by this scene.

Native Nav2 has data dependencies and periodic/event-triggered callbacks, including feedback and retries. A formal per-job DAG needs explicit job boundaries, precedence semantics and timing metadata. No mixed-criticality levels, WCET budgets, deadlines, offloading or custom scheduling baseline are introduced here.

## Verification and recordings

`scripts/run_monaco.sh` publishes the initial pose, checks live LiDAR and odometry, verifies core Nav2 lifecycle states and requests the 20 goals. Success requires action status 4, no missed waypoints, estimated final error at most 0.40 m and an AMCL-trace distance of at most 0.65 m to each requested target. These are simulation integration checks, not guarantees of real-time schedulability or ground-truth localization accuracy.

The report records the odometry travel distance, estimated trajectory, target transitions and wall-clock timestamps. `scripts/record_monaco.py` captures the actual Gazebo window from before the mission until after its result. Recording metadata permits synchronization with target feedback. Runtime evidence is placed under ignored `artifacts/`; the static `layout.png` is only a design drawing.

Recordings and verification should use a fresh simulation at the start pose. User-defined scheduling experiments and communication parameters are a later stage.

Recorded full-course run: 20/20 targets succeeded, no missed waypoints, 411.431 s wall time, 128.069 m odometry travel, and 0.140 m final Gazebo ground-truth error. Estimated final localization differed from ground truth by 0.490 m; AMCL estimates are labeled as such in the video. Evidence: `docs/evidence/monaco-full-course.json` and `docs/evidence/monaco-checkpoint-correction.json`.
