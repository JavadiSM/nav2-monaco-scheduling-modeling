# Monaco-inspired circuit

## Scene

This is a hand-designed, approximate Monaco silhouette, not an official scaled circuit. Geometry is specified in `config/monaco.yaml` and generated by `scripts/generate_monaco.py`. One red vehicle moves; 25 blue server cabinets with antennas stand outside the racing corridor. The original nineteen checkpoint-associated locations are preserved; two roadside start/finish endpoints and four infill endpoints complete the current layout. Each has a reserved edge-worker identity in `scenario.json`.

The centerline is approximately 126.0 m long and the road is 1.30 m wide. There are 19 ordered checkpoints before named turn approaches, followed by a finish target. Start and finish are approximately 3.0 m apart, separated by continuous barriers. A clearance-aware grid search found a roughly 122.0 m shortest traversable route before map wall rasterization; it is a geometric check, not measured robot travel distance. The generator rejects unintended short connections between nearby lanes. Four iterations of Chaikin corner cutting round the centerline while preserving straight sections. The accepted map, physical barriers, checkpoint poses and centreline remain frozen. `scripts/extend_rsu_layout.py` adds only roadside endpoints, preserving original endpoint poses and every non-RSU world element.

The simulated car is an existing differential-drive TurtleBot with changed visual geometry. Its four visible tires are decorative; physical driving remains the upstream two-wheel differential drive. The upstream collision dimensions, LiDAR, IMU, camera, joints, inertia and drive limits are retained. The body visuals remain below the LiDAR scanning plane so the sensor does not detect the car's cockpit as an obstacle.

Checkpoint 11 uses a 1.50 m approach lead instead of the default 0.55 m. Its target is placed before the chicane's direction reversal, with the incoming heading. The original waypoint-based full-course recording predates this placement correction; a focused test passed all three targets (10–12) in 84.2 s; it invoked 0 backup and 0 spin recovery behaviors.

## Navigation configuration

The planner, controller, smoother, behaviors, localization and waypoint follower remain upstream Nav2 components. The project supplies a map, starting pose and one ordered `NavigateThroughPoses` goal; it does not implement its own path-following controller. A copy of the installed pass-through behavior tree computes a path through the remaining checkpoints and keeps FollowPath active until the finish. Intermediate checkpoint yaw is not a separate stop-and-align requirement. Its RemovePassedGoals radius is 0.70 m and its replanning RateController is 1 Hz (the installed template uses 0.333 Hz); the controller still runs at 20 Hz.

Scenario changes relative to installed `nav2_bringup/params/nav2_params.yaml`:

- Local and global inflation radius: 0.34 m; cost scaling: 5.0, to fit the corridor.
- `GridBased.allow_unknown: false`, restricting planning to mapped drivable space.
- AMCL simulation profile: odometry alpha1–alpha5 0.01, 120 beams, sigma_hit 0.10 m, update_min_d 0.05 m, update_min_a 0.05 rad, z_hit 0.9 and z_rand 0.1. These are scenario assumptions for nearly deterministic simulated odometry, not measured parameters of a physical robot. Starting-pose covariance is 0.0025 m² for x/y and 0.0025 rad² for yaw.
- Pass-through behavior-tree RateController 1 Hz; installed navigation and recovery nodes are unchanged. At 0.46 m/s, checking goal removal once per second avoids a nearly 1.4 m travel gap between the template's 3 s replans.
- Waypoint follower stops on failure; waiting at each waypoint is disabled.
- Simulation time is enabled by launch. Scheduling policies and callback priorities are unchanged.

The occupancy map represents the road as free, physical barriers as occupied and outside space as unknown. Solid-filling outside space as occupied is unsuitable for this AMCL likelihood-field scene: points inside that filled area receive artificially good obstacle-distance scores. World wall coordinates and map pixels share the same transform.

Resource inspection and concrete settings are documented in `docs/resources-and-timing.md`. No per-edge CPU limits or alternative scheduling policies have been enabled.

## Communication and scheduling scope

Communication is feasible through ROS 2 / DDS, but a parked model is only a location and visual identity. Each current RSU is associated with an independent virtual two-A7/two-A15 server template. Extensible request/result cost functions currently return zero seconds, with 5 m coverage checked only when admitting a request. The live baseline still executes locally; offloading is a subsequent policy extension. See [extension interfaces](scheduling-interfaces.en.md).

`config/edge_communication.yaml` is inactive. Its null values are intentionally unspecified: publish rate in Hz, bandwidth in Mbps, latency in ms, loss probability and optional coverage radius. Values can later be defined per link. Application-layer emulation and network-layer shaping have different semantics; neither is implemented by this scene.

Native Nav2 has data dependencies and periodic/event-triggered callbacks, including feedback and retries. A formal per-job DAG needs explicit job boundaries, precedence semantics and timing metadata. No mixed-criticality levels, WCET budgets, deadlines, offloading or custom scheduling baseline are introduced here.

## Verification and recordings

`scripts/run_monaco.sh` publishes the initial pose, checks live LiDAR and odometry, verifies core Nav2 lifecycle states and requests the 20 goals. Success requires action status 4, a zero Nav2 error code, estimated final error at most 0.40 m and an AMCL-trace distance of at most 0.70 m to each requested target. Ordered estimated target visits are checked separately from action feedback. The pass radius matches the installed RemovePassedGoals behavior; it is not a relaxation of the final-position check. These are simulation integration checks, not guarantees of real-time schedulability or ground-truth localization accuracy.

The report records the odometry travel distance, estimated trajectory, target transitions, recovery count, odometry velocity samples and wall-clock timestamps. `scripts/record_monaco.py` captures the actual Gazebo window from before the mission until after its result. Recording metadata permits synchronization with target feedback. Runtime evidence is placed under ignored `artifacts/`; the static `layout.png` is only a design drawing.

Recordings and verification should use a fresh simulation at the start pose. User-defined scheduling experiments and communication parameters are a later stage.

Original waypoint-based full-course run: 20/20 targets succeeded, no missed waypoints, 411.431 s wall time, 128.069 m odometry travel, and 0.140 m final Gazebo ground-truth error. Estimated final localization differed from ground truth by 0.490 m; AMCL estimates are labeled as such in the video. Evidence: `docs/evidence/monaco-full-course.json` and `docs/evidence/monaco-checkpoint-correction.json`.

The first continuous full-course attempt with the generic localization defaults failed after about 102.5 m: final AMCL and Gazebo positions differed by about 0.71 m, and planning repeatedly reported no valid path. Its failed report and raw capture are preserved under `artifacts/monaco-smooth-attempt-1-*`. It is not completion evidence.

Current rounded-track continuous run: 20/20 ordered targets passed in 322.197 s wall time, with 122.050 m odometry travel and 0 Nav2 recoveries. Gazebo final goal error was 0.173 m; final AMCL-versus-Gazebo error was 0.041 m. Every intermediate checkpoint had an estimated closest pass within 0.148 m. Evidence: `docs/evidence/monaco-smooth-full-course.json`; recording: `artifacts/monaco-smooth-start-to-finish.mp4`. This is setup validation with a changed scene/mission configuration, not a scheduling-baseline performance comparison.

Odometry during the mission, excluding the first and last 2 s of the action interval, showed forward speed continuously above 0.212 m/s, a median of 0.460 m/s, and zero reverse samples below -0.02 m/s. This observation applies to this recorded run, not a guarantee for arbitrary future scheduling delays.
